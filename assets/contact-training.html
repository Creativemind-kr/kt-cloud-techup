01 · 레퍼런스 분석

컨택 가이드에서
가져올 핵심

기존 가이드의 장점은 정보량보다 “상담사가 지금 무엇을 해야 하는지”가 선명하다는 점입니다.

기존 컨택 가이드는 오프닝·클로징·전환 신호·필수 체크·FAQ·상태 관리를 한 화면에 모아 실제 연락 업무 중 바로 꺼내 쓰는 플레이북 구조입니다.

그대로 가져올 구조

① 짧은 오프닝 → ② 핵심 질문 → ③ 전환 신호 → ④ FAQ → ⑤ 다음 행동처럼 상담 행동 순서를 명확히 보여주는 방식은 교육용에도 매우 적합합니다.

교육용에서는 바꿀 부분

기존 가이드는 한 과정의 컨택 운영 중심입니다. TECH UP 교육용은 5개 과정의 차이를 판단하고 추천 근거를 말하는 능력을 중심으로 재구성하는 것이 좋습니다.

운영 정책 주의: 기존 컨택 가이드의 모집일·수업시간·카드·카메라·상태값 같은 운영 조건은 해당 가이드의 특정 과정 기준입니다. 이 교육자료에서는 구조만 참고하며, 실제 안내 값은 현재 TECH UP 공식 모집공고와 최신 상담자료를 우선합니다.

03 · 상담 흐름

상담은
6단계로

정보를 한 번에 쏟아내지 않고 학생의 답에 따라 다음 화면을 고릅니다.

STEP 1

관심 이유 확인

“이번 과정은 어떤 계기로 알아보셨어요?”로 시작해 취업·전향·실무 보완·포트폴리오 중 목적을 확인합니다.

STEP 2

원하는 일 확인

디자인 / 코딩 / 서버 / 서비스 전체 / 기획 중 어떤 일을 해보고 싶은지 먼저 구분합니다.

STEP 3

경험 수준 확인

Figma, React, Java, 기획서 작성 등 해본 경험을 듣되 경험 유무만으로 과정 적합도를 단정하지 않습니다.

STEP 4

1~2개 과정으로 좁히기

학생의 답을 다시 요약한 뒤 “말씀하신 기준이면 A가 가장 가깝고, B도 비교해볼 수 있습니다.”처럼 추천합니다.

STEP 5

결과물로 설득

커리큘럼 전부가 아니라 사용 도구 → 만드는 결과물 → 프로젝트 → 취업 결과물 순으로 보여줍니다.

STEP 6

우려 확인 후 다음 행동

“결정하시기 전에 가장 걸리는 부분이 뭐예요?”를 묻고, 최신 모집 기준에 따라 지원·상담 다음 단계를 안내합니다.

04 · 질문법

좋은 상담은
좋은 질문에서

정답을 알려주기 전에 학생이 어떤 기준으로 선택해야 하는지 스스로 말하게 만듭니다.

Q1 · GOAL

“교육 끝나고 어떤 결과물이 있으면 가장 좋을까요?”

학생이 ‘취업’이라고만 답할 때도 실제로 원하는 결과물을 구체화합니다.

듣기: 화면 디자인 / 실제 웹 / 서버 프로젝트 / 완성 서비스 / 기획서·서비스 출시
Q2 · INTEREST

“화면을 설계하는 것과 코드로 구현하는 것 중 어느 쪽이 더 끌리세요?”

프로덕트 디자인과 프론트엔드를 빠르게 구분하는 질문입니다.

듣기: 사용성·Figma → 디자인 / React·구현 → 프론트
Q3 · DEPTH

“화면보다 데이터나 서버 로직을 다루는 쪽도 흥미가 있나요?”

프론트·풀스택·백엔드 사이를 좁힐 때 유용합니다.

듣기: 서버 집중 → 백엔드 / 양쪽 모두 → 풀스택
Q4 · ROLE

“직접 만드는 역할과, 무엇을 만들지 정하고 팀을 조율하는 역할 중 어느 쪽이 맞나요?”

개발·디자인 과정과 PM 과정을 구분합니다.

듣기: 문제 정의·우선순위·협업 → 프로덕트 매니지먼트
Q5 · EXPERIENCE

“지금까지 해본 것 중 가장 재미있었던 작업은 뭐였어요?”

전공 여부보다 실제 흥미와 행동 경험을 확인합니다.

듣기: Figma / React / Java / 프로젝트 총괄 / 문서화 등
Q6 · CONCERN

“과정을 선택할 때 가장 걱정되는 건 무엇인가요?”

비전공, 난이도, 취업, 일정, 비용, 장비 등 실제 의사결정 장애물을 확인합니다.

듣기: 바로 반박하지 말고 걱정을 한 문장으로 다시 확인
05 · 과정 매칭

학생의 말 →
추천 과정

상담사가 추천 이유를 한 문장으로 설명할 수 있어야 합니다.

학생이 자주 하는 말우선 추천상담사가 연결할 근거
“앱 화면이나 UX에 관심이 있어요.”프로덕트 디자인화면을 코드로 만드는 것보다 사용자 문제를 찾고 Figma로 경험을 설계하는 비중이 큼.
“React를 배웠고 실제 웹을 만들고 싶어요.”프론트엔드사용자가 보는 화면을 구현하고 재사용·성능·협업까지 연결하는 결과물이 맞음.
“Java/Spring이나 서버 쪽으로 취업하고 싶어요.”백엔드데이터 저장, API, 서버 구성과 운영 역량을 깊게 가져가는 방향이 맞음.
“프론트와 백엔드 둘 다 해보고 싶어요.”풀스택화면부터 서버까지 연결해 하나의 서비스 전체를 완성하는 경험을 원하는 경우.
“아이디어를 기획해서 개발자·디자이너와 만들고 싶어요.”프로덕트 매니지먼트고객 문제, 우선순위, 일정, 데이터 판단과 협업을 중심으로 보는 경우.

VS

헷갈림 ③ 백엔드 vs 풀스택

백엔드서버·데이터·API를 중심으로 깊게

풀스택백엔드도 배우지만 화면 개발까지 함께

06 · AI 반박 스크립트

AI가 있는데
왜 배워요?

부정하지 말고 인정한 뒤, “AI 결과물을 실무 기준으로 완성하는 역량”으로 연결합니다.

COMMON FRAME · 공통 답변 구조

“맞아요. AI 덕분에 만드는 속도는 정말 빨라졌습니다. 그래서 이제 중요한 건 단순히 만드는 사람이 아니라, AI가 만든 초안을 기업 기준에 맞게 고르고 고치고 설명할 수 있는 사람입니다.”

“이 과정은 AI를 안 쓰는 교육이 아니라, AI를 도구로 쓰면서도 결과물의 품질과 책임은 사람이 가져갈 수 있게 만드는 과정입니다.”

PRODUCT DESIGN

프로덕트 디자인

AI가 이미지를 만들 수 있어도 브랜드 기준, 사용자 맥락, 화면 흐름까지 맞춘 제품 경험은 따로 설계해야 합니다.

멘트 · “AI스러운 시안을 기업 표준의 디자인 시스템과 사용 경험으로 바꾸는 과정입니다.”
FRONTEND

프론트엔드

멘트 · “보이는 화면을 실제 사용자 환경에서 문제없이 작동하게 완성하는 힘을 배웁니다.”

백엔드

멘트 · “작동하는 코드가 아니라, 버티고 관리되는 서버를 설계하는 기준을 배웁니다.”

풀스택

멘트 · “조각난 기능을 하나의 서비스로 연결하고 끝까지 완성하는 경험을 합니다.”
PRODUCT MANAGEMENT

프로덕트 매니지먼트

AI가 기획서 초안을 써도 무엇을 왜 먼저 만들지, 고객과 팀을 어떻게 설득할지는 사람이 결정합니다.

멘트 · “AI로 자료 작성 속도는 높이고, 사람만이 할 수 있는 판단과 협업을 훈련합니다.”
응대 주의: “AI는 한계가 있어요”로 시작하면 방어적으로 들릴 수 있습니다. 먼저 “맞아요, AI 덕분에 빨라졌습니다”라고 인정한 뒤, 기업 기준·책임·협업·완성도로 전환합니다.
07 · 핵심 컨택 스크립트

오프닝과 클로징이
컨택의 핵심

처음 30초에서 연락 목적과 다음 절차를 명확히 하고, 마지막에는 고객의 현재 온도에 맞는 다음 행동 하나만 제시합니다.

OPENING · 그대로 읽어도 되는 기본형

연락 목적 → 안내 범위 → 통화 가능 여부

“안녕하세요, ○○○님. KT 클라우드 캠프 운영팀 ○○○입니다. KT CLOUD TECH UP 클라우드 네이티브 과정 문의 주셔서 연락드립니다. 궁금하신 부분 확인 후, 수강 가능 여부와 Zoom 면접 신청 절차까지 안내드리겠습니다. 통화 가능하신 시간 있으실까요?”

오프닝에서 꼭 들어갈 3가지① 누구인지 · ② 왜 연락했는지 · ③ 어디까지 안내할지

상대가 통화 가능한지 먼저 확인한 뒤 상담으로 넘어갑니다. 첫 문장에서 과정 설명을 길게 시작하지 않습니다.

CLOSING · 3 PATTERNS

고객의 온도에 따라 마지막 한 문장만 바꿉니다.

01 · 바로 신청할 고객

“신청 페이지: [URL] / 마감 [마감일]입니다. 신청 완료하시면 카톡 주세요, 면접 준비 도와드릴게요.”

USE · 신청 의사가 명확할 때
02 · 자료 보고 결정할 고객

“자료 보내드릴게요. 보고 결정되시면 카톡 주세요, 다음 단계 같이 봐드립니다. 마감일까지 [N]일 남았어요.”

USE · 관심은 있지만 검토 시간이 필요할 때
03 · 공고부터 볼 고객

관심이 높아졌다는 신호

  • “비전공인데 따라갈 수 있나요?”
  • “프로젝트는 실제로 어떤 걸 만들어요?”
  • “프론트랑 풀스택 중 취업에는 뭐가 더 맞아요?”
  • “포트폴리오는 어느 정도까지 나오나요?”
  • “지원하려면 다음에 뭘 하면 돼요?”

⚠ 바로 확인해야 하는 신호

  • “일하면서 병행 가능한가요?” → 최신 운영시간 확인
  • “교육비는 정확히 얼마예요?” → 최신 지원 기준 확인

  • “취업 보장되나요?” → 보장 표현 금지, 지원 범위로 설명
  • “무조건 이 과정이 제일 좋은 거죠?” → 목적에 따른 적합도로 다시 설명
09 · FAQ 대응

외우기보다
답변 구조를

사실값은 최신 모집자료를 확인하고, 상담사는 답변의 프레임을 익힙니다.

비전공자도 가능한가요?

전공 여부만으로 가능·불가를 단정하지 않습니다. 먼저 지금까지 해본 경험과 목표 직무를 확인하고, 상담자료의 추천 대상과 기초→프로젝트 흐름을 근거로 설명합니다. “비전공이라도 무조건 가능”처럼 보장하지 않습니다.답변 구조 · 경험 확인 → 과정의 시작점 설명 → 프로젝트 결과물 연결

어떤 과정이 취업에 제일 좋아요?

과정별 우열이 아니라 목표 직무가 다르다고 설명합니다. “어떤 일을 하고 싶은지”를 다시 묻고 프로덕트 디자이너·프론트·백엔드·풀스택·PM 중 목표 직무와 맞는 과정을 추천합니다.답변 구조 · 우열 질문을 적합도 질문으로 바꾸기

AI가 있는데 이 과정을 왜 배워야 하나요?

먼저 “맞아요, AI 덕분에 만드는 속도는 빨라졌습니다”라고 인정합니다. 그 다음 기업은 그럴듯한 초안보다 브랜드 기준, 보안, 성능, 사용자 경험, 협업 맥락까지 맞춘 결과물을 원한다고 설명합니다. 과정별로는 위의 AI 반박 스크립트에서 해당 과정 멘트를 골라 연결합니다.답변 구조 · 인정 → 기업 기준 → 과정별 역할 → 프로젝트 경험

교육비·지원금·일정은 어떻게 되나요?

숫자는 교육자료에 외워 적어두지 않고 최신 상담자료와 공식 모집 기준을 확인해 안내합니다. 특히 모집일, 교육기간, 지원금, 본인부담금은 변경 가능성이 있는 운영값으로 취급합니다.답변 구조 · 최신값 확인 → 조건 설명 → 학생에게 해당 여부 확인

프로젝트가 정말 취업에 도움이 되나요?

‘도움이 된다’고만 말하기보다 과정별 결과물을 보여줍니다. 디자인은 Figma 시제품과 디자인 시스템, 프론트는 작동하는 웹, 백엔드는 서버 프로젝트, 풀스택은 화면+서버 서비스, PM은 기획서와 서비스 운영 경험처럼 구체적으로 설명합니다.답변 구조 · 결과물 예시 → 어떤 역량을 증명하는지 → 포트폴리오 연결

10 · 표현 가이드

잘 말하는 것보다
정확하게 말하기

컨택 가이드의 금지어·주의 표현 구조를 교육용으로 확장합니다.

🚫 상담 중 하면 안 되는 멘트는 ‘주의’가 아니라 금지입니다.취업 보장, 전망 단정, 누구나 가능, 확인하지 않은 일정·비용 확답처럼 결과를 보장하거나 사실값을 단정하는 표현은 사용하지 않습니다.

✓ 이렇게 말하기

  • “말씀하신 목표 기준으로는 이 과정이 더 가깝습니다.”
  • “취업 시 보여줄 수 있는 프로젝트 결과물을 만드는 과정입니다.”
  • “현재 상담자료 기준으로 확인해서 안내드릴게요.”
  • “두 과정의 차이는 어떤 역할을 더 깊게 경험하느냐입니다.”
  • “지원 전에 가장 걱정되는 부분을 먼저 확인해볼게요.”

🚫 하면 안 되는 멘트 · 금지 표현

  • “이 과정 들으면 무조건 취업돼요.”
  • “비전공자도 누구나 문제없이 따라가요.”
  • “이 과정이 다섯 개 중 제일 전망 좋아요.”
  • 확인하지 않은 일정·비용·지원 조건을 기억에 의존해 단정
  • 학생 답을 듣기 전에 “그러면 무조건 ○○ 과정”으로 바로 결정
